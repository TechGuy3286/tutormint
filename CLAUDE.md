# TutorMint — rules for Claude Code

TutorMint (tutormint.org) connects verified tutors with parents and schools/academies in Pakistan. Browsing is free; what is sold is the tutor's one-time Verification Fee and, by bank transfer, tutor Premium and parent Featured (PR-13).

**Change history: docs/history/ — read only when a task needs past context.** This file holds the rules in force only. When a PR changes a rule, edit that rule here in place (one or two lines) — never add a dated section. Dated notes go in `docs/history/<yyyy-mm>.md`. The schema ledger is `supabase/migrations/`.

**Precedence.** This file wins over docs/history. If a rule here conflicts with code or with an owner instruction that this file does not settle, stop and ask the owner — do not pick one silently.

## Project and stack

- Next.js 16 App Router (`proxy.ts`, not middleware — read `node_modules/next/dist/docs/` before Next code), TypeScript, Tailwind v4. **Supabase only** (Postgres + Auth + Storage); Mongo is gone, never re-add it.
- Production Supabase: Mumbai `yhekiqtelsictqkfxrfj` (ap-south-1). Vercel functions `bom1`. **Production serves the `rebuild` branch** — every push to it is a release. One database serves preview and production; any script that writes goes through `scripts/target.ts` `guardWrites()`.
- Email: Resend, only through `lib/email/send.ts` (also Supabase Auth SMTP via Resend). SMS: **SendPK only** (`SENDPK_API_KEY/SENDER/TEMPLATE_ID/BASE_URL`); it sends only the approved verification-code template, so free-text SMS is impossible. `BRIDGE_OTP` + `BRIDGE_OTP_EXPIRES` is a time-boxed backstop. AI: `lib/ai/anthropic.ts` (server-only; model is one constant there; `ANTHROPIC_API_KEY` exists only in production). **The AI never receives a phone number** (PR-18): text bound for it is redacted first (`lib/postRedactCore.ts` `redactForAi` — mobiles in any format, CNIC shapes, 10+ digit runs, emails → placeholders; Urdu/Arabic-Indic digits ۰–۹ ٠–٩ count as 0–9 and come out in English digits, PR-21) in the browser AND again on the server, which refuses to call it while `hasNumberLeft`; pasted text is never logged or stored. An **image** bound for it (PR-20/PR-21, `lib/imageRead.ts` / `lib/imageMaskCore.ts`) is read in memory **on the server** by plain OCR first (tesseract.js + bundled `@tesseract.js-data/eng` and `urd`; no AI — Urdu-model lines only when they name a contact word such as رابطہ, and Urdu-model digit words only where the English model read no confident word, `urduDigitWords`: 7+ on a line are masked), every number/email box is blacked out, the masked image is OCR-read again, and the AI gets only the masked image — any number still readable (7+ Urdu digits included), or any OCR/masking error → the AI is not called ("Couldn't read this image safely — please type the details."); images are never stored or logged. tesseract.js starts its worker by file path, so tracing never follows it: `next.config.ts` ships it and every package it depends on (computed from package.json, `packageTree`) with the route — PR-21's production failure was the worker missing `bmp-js`. The route runs 120 s (OCR 70 s in all, 30 s a step, a hung worker is dropped; AI 35 s), always answers JSON with a plain message (too large / photo type / took too long / AI busy / couldn't read safely), and a failure writes `tuition.ai_fill_failed` (technical reason only) to the Audit log — "Paste a post" too. Google Indexing API + Search Console read via a service account (`GOOGLE_INDEXING_CLIENT_EMAIL/PRIVATE_KEY`). YouTube for intro videos (`YOUTUBE_*`).
- Payments: **bank transfer with a receipt only**. **PayPro has ended** (PR-12): no code calls PayPro or reads a `PAYPRO_*` variable (the env vars may be deleted); `/paypro/uis` only logs a late callback and adds one `paypro_late` Finance alert per order, ever — nothing activates; it is rate-limited to 20 requests an hour per IP (`paypro_callback` bucket, PR-14) and an excess request gets a plain 429 that is not logged (`pay.paypro.cutoff` = 2026-11-19). Past PayPro payments stay readable with their labels. AssanPay and the simulator are removed.
- Local machine (Windows): no psql — production SQL runs through `pg` from a `scripts/*.ts` file; `npx tsx --env-file=.env.local`; tsc/build need `NODE_OPTIONS=--max-old-space-size=6144` (8 GB RAM: one build/tsc at a time).

## Deploy and the standard PR ending

1. Migrations: additive, idempotent, no `begin/commit` in the file; run the `scripts/apply-migration-NNN.ts` dry run (rolled back) first, then apply **before** pushing the code that needs it. Never a data change on production without a backup/dry run.
2. Gates (all must pass): `npx tsc --noEmit`, `npm run build`, `npm run check:contrast`, `npm run rls:audit`, `npm run check:counts` (read-only, production), the relevant `test:*` suites (there is no "all tests" script — loop over every `test:*` except `*:live`), and `npm run test:staticrender` when public pages are touched.
3. Commit, then `git push` to `rebuild`. **Never `vercel --prod` or `vercel promote`.** If a Vercel status check hangs, confirm on the live site.
4. Read-only smoke test on https://www.tutormint.org (pages load or redirect, no error). Report any breakage with the exact URL and what you saw; do not fix it in the same pass unless told to.
5. Update the affected rule in this file in place; put dated detail in `docs/history/`.

## Engineering rules

- **Auth truth = the Supabase cookie session.** Never localStorage/sessionStorage for login or role (sessionStorage may hold an unsaved draft or list scroll only). Role is `profiles.role` (`tutor | parent | admin`); staff also have `profiles.admin_role`. Never probe tables to guess a role.
- Role gating is server-side in `app/tutor/layout.tsx`, `app/parent/layout.tsx`, `app/admin/layout.tsx`. Every write route calls `supabase.auth.getUser()` first and scopes to that user. Admin routes use `checkAdminRole` / `requireAdminRole` with `SCREEN_ACCESS` (`lib/adminAuth.ts`) — the single access list for nav, screens and routes. A screen hidden in the UI must also be refused by the route.
- Entitlements are enforced server-side (`lib/entitlements.ts` `getEntitlements`, RLS, `lib/quota.ts` check-then-consume). Suspension is checked before tier. Contact fields are never sent to a client without the right — filter in the route, not JSX.
- **Every admin count comes from `lib/counts`** (rules `lib/countsCore.ts`, PR-14): the same count must match on every screen that shows it, and `npm run check:counts` must pass. One definition per count (`COUNT_DEFS`: New tutors/parents/sign-ups, Mobile verified, Tutors verified mobile, Tutors finished onboarding, Document uploads, Paid, Plans bought, Tuitions posted, Applications, Applications forwarded, Contact number viewed), Pakistan-time windows from `trendWindows` (Last 7 days = today + the six full days before). Member counts use the People rule (`excludedReason`: staff, seed, team, test, hidden, merged, erased, erase-requested out); staff ACTIONS count where the action is what is counted (tuitions posted through the team account, forwards, WhatsApp sends — `actorCounts`). A sign-up is an account, never the `registered` event. Two cards with one name never show two numbers; a count that intentionally differs gets its own label (e.g. "Then paid", "Of them: paid").
- **Every mutation logs:** `logActivity()` (`lib/activityLog.ts`) for members; admin mutations also `admin_audit_log` (`logAdminAction`). Never a message body, phone, CNIC or email in a log or audit row.
- **No free-text subjects.** Subjects/levels are `taxonomy_master` ids (`tutor_subjects`, `job_subjects`), read via `lib/taxonomy.ts` (non-legacy rows only in pickers; `labelsForMasterIds` renders legacy ids). Max **15 distinct subjects** per tutor (`lib/subjectLimitCore.ts`).
- **No search buttons** — every search input is a typeahead (`components/search/Typeahead.tsx`, debounce, `suggest={false}` on admin lists). Applications and admin Tuitions searches also find a tuition by `JOB-TX-…` or `TM-…`, any case, with or without the prefix (`lib/jobCodeSearchCore.ts`).
- No hardcoded secrets, emails, phone numbers or mock data in shipped pages; contact and pay details come from `app_settings` with env fallbacks. No sample data as a form default. No fabricated ratings, counts or reviews.
- Validation: `lib/validate.ts` `parseBody` (Zod; use `z.guid()` not `z.uuid()`); plain human errors, never Zod text. Rate limits live in the DB (`consume_rate_limit`, fails open).
- PostgREST max rows is 1,000 — whole-list reads go through `lib/pageAll.ts`; never `.limit(>1000)` (`test:pagecap`). When asking whether RLS allows something, probe in SQL, not over REST.
- Server code may not import a non-component value from a `'use client'` module (`check:server-imports` runs as prebuild). A client component must never import a file that imports `node:crypto`.
- In-memory caching only: `lib/memoCache.ts` `memoize()` / `invalidateMemoTag()` — no `unstable_cache`, no Data Cache.
- Times: Pakistan time (`Asia/Karachi`) for every day/week/month count; client relative times through `<TimeAgo>`; formatters always pass a `timeZone`.
- `rank_tutors()` must stay `plpgsql` with `SET plan_cache_mode = force_custom_plan` (else signed-in Browse times out). It reads the precomputed `tutor_rank_cache` (PR-17, migration 243; labels, tier, score per listed tutor, the listing still gated live on `tutor_directory`), refreshed by `refresh_tutor_rank_cache()` every minute by **pg_cron inside the database** (job `tm-rank-cache-refresh`, PR-18 migration 245; ~0.3 s, only changed rows written; the Vercel admin cron only steps in when the last full refresh is over 3 minutes old — `refreshRankCacheIfStale`) and per tutor on a rating change; a cache older than 10 minutes falls back to `rank_tutors_live()` (the old body). A failed ranking never shows an error page: `lib/browseTutors` falls back to `rank_tutors_simple()` (`lib/rankFallbackCore.ts`). Landing pages read `landing_combinations_fast()` (stored counts), never the view page by page.
- After adding a constraint, check the column DEFAULT and triggers too. A public-only dump does not carry `on_auth_user_created` — re-verify it after any restore. `lib/ensureProfile.ts` is the authoritative profile upsert on every user-creating path.

## Security and privacy

- **PERMANENT — TutorMint has exactly one Owner (Alee Sabeer), forever.** Ownership can never be transferred. No role, screen, route, script or migration may create a second Owner, change the Owner's role, or suspend, ban, merge, pause, remove or delete the Owner — nobody can change the Owner's role, access or account. The database enforces it for every caller incl. the service role (migration 215: unique index `profiles_single_owner` + trigger `guard_single_owner`); never write code that disables it.
- **Owner-only actions** (others get 403 and the Owner gets the blocked-attempt alert — `lib/ownerGuard.ts`): suspend / reinstate / ban / lift a ban; change a member's mobile; edit a CNIC number; clear mobile verification; read the CNIC number from a photo; unlock a document for re-upload; rotate/crop a photo; change an already-approved document; approve a home address; reject any payment receipt; approve a receipt with no matching bank credit; reopen a rejected receipt; plan grants; merge, convert account type, close-and-erase, View as; team, roles, staff pause/remove/restore, targets, city owners; Finance actions (link credits, statement import, personal marks, re-label, fee match range, bank details, gateways, refunds); template wording approval; Withdraw a contact / Do not use list; posting a withdrawn / erased / on-hold number (with a logged reason); Notification settings (incl. "Who gets OTP alerts"), support number, Privacy; reassigning or releasing another staff member's "I'm on it"; Locations approvals; Undo of staff document decisions; Allow / Keep blocked on Blocked re-sign-ups.
- **Every staff role needs two-factor.** A paused staff member has no admin access; their cities and tuitions go to the Owner.
- Masking: phones in admin lists are masked with a logged **Show** (`member.contact_reveal`); CNIC numbers show `XXXXX-XXXXXXX-4`, full number only to the Owner, Project Manager and Backend Support with a logged Show (`cnic.reveal`, written before the value is returned); home addresses the same way — masked "•••••• (City)" with "Read from CNIC — not confirmed" / "Confirmed by member", full address only through the same reviewers' logged Show (`address.reveal`), never public; bank/account numbers show the last 4. Synthetic `@users.tutormint.org` addresses are never displayed (`shownEmail()`). Parents, the public and other tutors never see any part of a CNIC.
- Message number masking: digits that are a Pakistani mobile or CNIC (shape test, `lib/masking.ts`) render masked when either side of the pair lacks contact rights; stored raw.
- Identity documents live only in the private `identity-docs` bucket, served via `/api/documents/[id]/preview` (private, no-store; never through the image optimiser); receipts in private `payment-proofs`. A new document kind is private by default.
- No chat-browsing screen: message bodies load in admin only for a reported message/thread. Official messages use `admin_messages` (Team channel), not `threads`.
- No test data in production; the seed cast is fixed (`npm run reset:seedcast` restores and asserts it). Test-named (`is_test_name`), seed, team and `hidden_from_public` accounts are out of Browse, search, sitemap and every count.
- Credentials only in env; never printed, logged or committed. Never log a phone, email, CNIC, account number, OTP or key.
- View as (Owner only) never signs in as the member: reads run as that member through `lib/viewAsContext.ts`; every write is refused.

## Roles and rights

`admin_role` values (internal → shown as): `owner` → Project Manager ("account owner" only on the Owner's own Team card); `partner` → Project Manager; `supervisor` → **Manager**; `admin`, `operations`, `tuitions_staff`, `backend_support` → badge "Admin" (real role visible to Owner/Partner). Labels: `ROLE_LABEL`, `roleBadge()` in `lib/adminAccessCore.ts`. Lists are derived (`WORKING_STAFF_ROLES`, `POSTING_STAFF_ROLES`, `PARTICIPANT_ROLES`).

- **Owner** — everything; the only one for the Owner-only list.
- **Partner (Project Manager)** — sees every screen; writes only where the access list names `'partner'` (tutors, parents, people, tuitions, applications, documents view/rotate, reports, inbox); decides CNIC/photo/selfie and approves bank-matched fee receipts like Backend Support (`roleMayWrite`; DB `is_admin_writer` vs `is_admin_full_writer`).
- **Admin** — full operations except the Owner-only list; sees Payments status without amounts.
- **Manager (supervisor)** — Operations' screens, sees everyone's data, changes only their own tuitions and tutors in their own cities (`lib/supervisorScope.ts`); the Parent interest inbox for their own rows (PR-10).
- **Operations** — office staff: verification queues (view), posting, People, follow-ups, SEO, blog, social.
- **Tuitions staff** — post tuitions, Applications, Team activity (own), People → Tutors only; the Parent interest inbox for their own rows (PR-10).
- **Backend Support** — Overview (no money), People and every tutor/parent screen with their actions (PR-12: `tutors`, `parents`, `users`, `orphans`, slug, video visibility, member sessions — Owner-only decisions inside stay refused by `lib/ownerGuard`), follow-ups and Applications on any tuition, post tuitions (edit only its own), My sign-ups, WhatsApp updates (Today every row; Parent interest own rows). **Every row + badge totals on Applications and the Parent interest inbox** go to the Owner/Partner by role and to accounts on the `app_settings 'staff.all_rows'` grant (Mohsin) — `lib/staffAllRows.ts`; **Admin → Insights** to accounts on its own grant `app_settings 'staff.insights'` (Mohsin, PR-16, migration 242 — `requireInsights`); other Backend Support staff get neither; decides CNIC/photo/selfie (not the Owner-only cases; CNIC only when its number is on file, after ticking "name matches"); approves a Verification Fee receipt only when exactly one unlinked bank credit in the fee range, within 48 h, matches the payer's name (`lib/staffReceiptCore.ts`). Never Finance, revenue, bank details, settings, roles, merges or templates (DB restrictive policies block its token from payment/finance tables).
- Amounts (rupees) are shown only to `SCREEN_ACCESS.paymentAmounts` (Owner, Partner); everyone else gets `withoutAmounts()`.
- Staff decisions on documents are stored in `staff_document_decisions`; the Owner sees a daily list (Trust → Documents by staff) and can Undo.
- Former staff (`makeFormerStaff`, also used by "Remove from team") keep their history; sessions revoked, link deactivated (credits go to Admin), cities/tuitions handed to the Owner.

## Business rules in force

- **Feels free.** Browsing is public; sign-in is asked only at a transactional action (apply, post, message, view contact, pay), in a small modal that keeps the draft and returns the visitor afterwards (`lib/returnTo.ts` `safeReturnTo`).
- **Verification Fee** — Rs 199, one-time, never "/month", name always **"Verification Fee"** (Urdu تصدیقی فیس), non-refundable. **Upgrades on sale by bank transfer (PR-13):** tutor Premium and parent Featured — "Upgrade to …" on /membership-plans (signed out → sign-in, back to the card; unpaid tutor → the fee first) → /pay/choose receipt + tick → Owner approval activates 30 days (`lib/payments/activate.ts`); the same plan again extends 30 days from its end date, a higher plan replaces with a fresh 30 days, downgrades are never offered and refused (`lib/planPurchaseCore.ts`, `lib/planPurchase.ts`). Tutor Featured is on sale too (PR-14; `PAUSED_UPGRADE_CODES` is empty): its "Matched tuitions on your WhatsApp" line is delivered through People → WhatsApp updates (see below); promotion (`PROMOTE_UPGRADES`: nudges, upsells, Renew reminders) stays off until the Owner turns it on. No refunds, ever. **Non-refundable notice** (`lib/nonRefundableCore.ts`, exact wording): shown above Submit on /pay/choose (a monthly plan shows `NON_REFUNDABLE_PLAN_NOTICE`) with the required tick "I understand the fee is non-refundable" (refused on `/api/payments/receipt` without it; time stored in `payments.non_refundable_ack_at`), in Terms → Fees and refunds (+ the charged-twice line), in the FAQ, and "This fee is non-refundable." on the fee and plan receipt emails and in-app messages. Never an amount in it.
- Tutor plans: Basic (free after the fee), Premium, Featured — see `plans` rows. Displayed quota "Unlimited" hides a real cap; admin sees real numbers.
- **Verified badge** (tutor) = fee paid + CNIC and profile photo submitted and neither rejected (`lib/badgeRule.ts`). Parent badge = CNIC + address approved. Badges never shown that entitlements did not grant. **Plan badges are English only** (PR-15): icon + "Verified" / "Premium" / "Featured", one shell (`components/badges/BadgeBase.tsx`), no Urdu label; a tutor profile/card shows ONE badge row — no separate "CNIC verified" chip and no FEATURED pill (`FeaturedTag` stays on Featured tuition cards only).
- **Listing** (`tutor_directory`, mirrored by `lib/tutorListingStatus.ts` `directoryBlockers`; `npm run test:directory:live`): role tutor, not suspended/banned/self-paused/under review/hidden/test/seed/team, verification not suspended/rejected, claimed if imported, no rejected CNIC or photo. The fee is not a listing condition. Profile completion only affects ranking and gaps (`profileGaps`).
- **Selfie is optional everywhere.** Badge, indexing, People stages, status image, social posts rest on CNIC + profile photo. An uploaded selfie still goes to review ("Selfie checked ✓" on the admin member page and inside the Edit Profile selfie card only — not on the dashboard top card, PR-16). On Edit Profile the selfie is in **Step 2 — Optional**; the step counts count exactly the rows shown (`groupStepCount`).
- **Tutor dashboard** (PR-16, PR-17): tiles are square and shadowed (icon centred on top, big number, label, own tone; slightly shorter than other dashboards), two to a row on a phone, four on desktop; ONE "Your next step" card (`components/tutor/NextStepCard.tsx`: "Continue: <step> (step X of 16)" to that exact step, the remaining steps as chips — never Tagline & About, which AI writes inside onboarding — and "N tuitions in <city> are waiting for you"; then "Pay the Verification Fee"; hidden when nothing is left) replaces the completion chips and the value card; "Your profile on Google" sits last, collapsed; beside the name an unpaid tutor sees a grey "Not verified yet" chip; My applications reads "N applied" (the Hired tile shows hires); intro video "Add video" / "Added ✓"; application titles display in normal case (`lib/titleCaseCore.ts`, display only); the plan chip is a plain link to /membership-plans. Edit Profile is a compact list (icon · label · Completed/Missing/Locked/Under review · chevron), locked rows (Mobile, CNIC, a set Email) say "To change this, contact support on WhatsApp 0321 5872222" with a WhatsApp button, and Pause / Delete sit in a red **Danger zone** at the bottom.
- **Profile completion** is one rule, `lib/profileRequired.ts` (16 items for a tutor without a selfie, the fee included; name, city, verified mobile for parents). Email, intro video and selfie never count. **One progress number everywhere** (PR-17): "X of 16 steps done" (`lib/onboarding/progressCore.ts`) — onboarding dashes (one per item, done dashes tappable), the dashboard top card, "Your next step", the Google card and the bell; no separate % figure.
- **Onboarding resume** (PR-17): every entry opens the first unfinished step (never step 1; no mobile-first gate — the mobile is asked in its own Contact step, only when not verified); each step saves on Next; Back (bottom, keeps typed text) + Next with a hint when disabled + "Save and finish later" (once city + subjects exist). Until finished the dashboard and ONE kept-current bell line say "Continue onboarding (X of 16)" (`lib/onboardingNotice.ts`, kind `onboarding_continue`).
- **Locked fields** (member side): mobile once verified, CNIC number + pictures once approved, email once a real address is the sign-in address. Everything else is editable any time; a replaced approved photo/selfie waits for review while the approved one stays public (`hold_member_photo` trigger). Upgrade to Featured to hire more." with Membership Plans; Featured shows "Unlimited hires" over a hidden cap (100) — `lib/parentHireCore.ts`, enforced in `hireApplicant` and `/api/gate`. Hire reviews keep their approval step. No AggregateRating / review JSON-LD (schema.org Person has none). - Landing/hub thresholds: city × subject pages need 3 live items (verified tutors / open tuitions); the main city tuition page is indexable from 1; variants (female/online/area/school) need 3; below it pages render `noindex, follow`. - **Tutor crawl links** (`lib/tutorCrawlCore.ts`, `lib/tutorCrawl.ts`): `/tutors/<city>` and `/tutors/<city>/female` list the city's tutors with numbered pages (?page= → `/qs/tutors/*` twins), indexable from 3 indexable tutors (3 women for the variant), in `/sitemap-pages.xml`, linked from /browse/tutors and the homepage city area (names only). Each open tuition links ≤ 6 indexable tutors (same city → subject/level → gender preference); each indexable profile links ≤ 6 similar indexable tutors (same city and subject). **A tutor who leaves the indexable set** (suspended, banned, hidden, erased, document rejected — any path) rebuilds at once exactly the pages that showed them — other profiles' Similar tutors, open tuitions' matching tutors, their city tutor pages, /browse/tutors, their own profile (PR-16, `lib/tutorLinkersCore.ts` decides against the set as it was; `lib/tutorLinkers.ts` `syncListedTutors()` from the 1-minute admin cron and the moderation route; snapshot `admin_summary 'crawl-listed'`, public facts only; the same marks again after 6 minutes, past every server's 5-minute crawl-set memory). The Indexing API is never used for profiles.
- **JobPosting** only on open tuitions: description from fields, `employmentType` always, `baseSalary` only with a fee, `validThrough` = base + 20 days, `identifier` = TM number, `hiringOrganization` = TutorMint (or the named school), TELECOMMUTE for online.
- **Indexing API** sends only tuition pages: URL_UPDATED on post/edit/resume/refresh/pause, URL_DELETED only once a page is noindex; ≤ 200 per Pacific day; queued in `indexing_queue`, never during a cached build.
- **Blog** (PR-20): the editor's figure checker never flags class/grade levels ("Class 4", "class 1 or class 2", "classes 6 to 10", "Grade 9–10", "9th class", O/A Level years — `LEVEL_NUMBER_RE`, `lib/ai/blogBrief.ts`); each flagged figure has ONE "Fix it with AI" button (rewrites only that sentence without the number, shown inline with Keep / Undo — `lib/blogFigureFixCore.ts`) beside the unchanged source-confirm field. Cluster, audience, language, city, subject, related landing pages and cover alt text fill themselves from the title (and the draft) — `lib/blogAutoSettingsCore.ts`; related pages only on a true city + subject/level match (a Pakistan-wide post gets none); a field staff change by hand is stored in `posts.hand_set` and never auto-filled again. `{{live-jobs}}` and the end-of-post block show at most 3 compact cards (`components/blog/CompactJobCard.tsx`: title, place, one level/subject line, View) — matches first, fewer shown as they are, none → the 3 newest in the block's scope (a Live jobs block only). The post page has the breadcrumb only (no "Back to Blog").
- Titles ≤ 60 (`seoTitle`), descriptions ≤ 155. Organization + WebSite JSON-LD are emitted site-wide by `SiteChrome` (Organization: name, legalName, url, logo, sameAs incl. the Google profile, areaServed Pakistan, city-only address, customer-support contactPoint with phone + email); tutor profiles are ProfilePage + Person (no invented rating/offers). `/llms.txt` exists; robots allows all crawlers.
- Only real searches count as demand (`lib/searchCountCore.ts`: bots, own crawlers, staff, cookieless first hits and 30-min repeats are not counted); search rows are written by the browser beacon, not the page render.
