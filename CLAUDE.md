# TutorMint — rules for Claude Code

TutorMint (tutormint.org) connects verified tutors with parents and schools/academies in Pakistan. Browsing is free; what is sold is the tutor's one-time Verification Fee and, by bank transfer, tutor Premium and parent Featured (PR-13).

**Change history: docs/history/ — read only when a task needs past context.** This file holds the rules in force only. When a PR changes a rule, edit that rule here in place (one or two lines) — never add a dated section. Dated notes go in `docs/history/<yyyy-mm>.md`. The schema ledger is `supabase/migrations/`.

**Precedence.** This file wins over docs/history. If a rule here conflicts with code or with an owner instruction that this file does not settle, stop and ask the owner — do not pick one silently.

## Project and stack

- Next.js 16 App Router (`proxy.ts`, not middleware — read `node_modules/next/dist/docs/` before Next code), TypeScript, Tailwind v4. **Supabase only** (Postgres + Auth + Storage); Mongo is gone, never re-add it.
- Production Supabase: Mumbai `yhekiqtelsictqkfxrfj` (ap-south-1). Vercel functions `bom1`. **Production serves the `rebuild` branch** — every push to it is a release. One database serves preview and production; any script that writes goes through `scripts/target.ts` `guardWrites()`.
- Email: Resend, only through `lib/email/send.ts` (also Supabase Auth SMTP via Resend). SMS: **SendPK only** (`SENDPK_API_KEY/SENDER/TEMPLATE_ID/BASE_URL`); it sends only the approved verification-code template, so free-text SMS is impossible. `BRIDGE_OTP` + `BRIDGE_OTP_EXPIRES` is a time-boxed backstop. AI: `lib/ai/anthropic.ts` (server-only; model is one constant there; `ANTHROPIC_API_KEY` exists only in production). Google Indexing API + Search Console read via a service account (`GOOGLE_INDEXING_CLIENT_EMAIL/PRIVATE_KEY`). YouTube for intro videos (`YOUTUBE_*`).
- Payments: **bank transfer with a receipt only**. **PayPro has ended** (PR-12): no code calls PayPro or reads a `PAYPRO_*` variable (the env vars may be deleted); `/paypro/uis` only logs a late callback and adds one `paypro_late` Finance alert per order, ever — nothing activates; it is rate-limited to 20 requests an hour per IP (`paypro_callback` bucket, PR-14) and an excess request gets a plain 429 that is not logged (`pay.paypro.cutoff` = 2026-11-19). Past PayPro payments stay readable with their labels. AssanPay and the simulator are removed.
- Local machine (Windows): no psql — production SQL runs through `pg` from a `scripts/*.ts` file; `npx tsx --env-file=.env.local`; tsc/build need `NODE_OPTIONS=--max-old-space-size=6144` (8 GB RAM: one build/tsc at a time).

## Deploy and the standard PR ending

1. Migrations: additive, idempotent, no `begin/commit` in the file; run the `scripts/apply-migration-NNN.ts` dry run (rolled back) first, then apply **before** pushing the code that needs it. Never a data change on production without a backup/dry run.
2. Gates (all must pass): `npx tsc --noEmit`, `npm run build`, `npm run check:contrast`, `npm run rls:audit`, `npm run check:counts` (read-only, production), the relevant `test:*` suites (there is no "all tests" script — loop over every `test:*` except `*:live`), and `npm run test:staticrender` when public pages are touched.
3. Commit, then `git push` to `rebuild`. **Never `vercel --prod` or `vercel promote`.** If a Vercel status check hangs, confirm on the live site.
4. Read-only smoke test on https://www.tutormint.org (pages load or redirect, no error). Report any breakage with the exact URL and what you saw; do not fix it in the same pass unless told to.
5. Update the affected rule in this file in place; put dated detail in `docs/history/`.

## Engineering rules

- **Auth truth = the Supabase cookie session.** Never localStorage/sessionStorage for login or role (sessionStorage may hold an unsaved draft or list scroll only). Role is `profiles.role` (`tutor | parent | admin`); staff also have `profiles.admin_role`. Never probe tables to guess a role.
- Role gating is server-side in `app/tutor/layout.tsx`, `app/parent/layout.tsx`, `app/admin/layout.tsx`. Every write route calls `supabase.auth.getUser()` first and scopes to that user. Admin routes use `checkAdminRole` / `requireAdminRole` with `SCREEN_ACCESS` (`lib/adminAuth.ts`) — the single access list for nav, screens and routes. A screen hidden in the UI must also be refused by the route.
- Entitlements are enforced server-side (`lib/entitlements.ts` `getEntitlements`, RLS, `lib/quota.ts` check-then-consume). Suspension is checked before tier. Contact fields are never sent to a client without the right — filter in the route, not JSX.
- **Every admin count comes from `lib/counts`** (rules `lib/countsCore.ts`, PR-14): the same count must match on every screen that shows it, and `npm run check:counts` must pass. One definition per count (`COUNT_DEFS`: New tutors/parents/sign-ups, Mobile verified, Tutors verified mobile, Tutors finished onboarding, Document uploads, Paid, Plans bought, Tuitions posted, Applications, Applications forwarded, Contact number viewed), Pakistan-time windows from `trendWindows` (Last 7 days = today + the six full days before). Member counts use the People rule (`excludedReason`: staff, seed, team, test, hidden, merged, erased, erase-requested out); staff ACTIONS count where the action is what is counted (tuitions posted through the team account, forwards, WhatsApp sends — `actorCounts`). A sign-up is an account, never the `registered` event. Two cards with one name never show two numbers; a count that intentionally differs gets its own label (e.g. "Then paid", "Of them: paid").
- **Every mutation logs:** `logActivity()` (`lib/activityLog.ts`) for members; admin mutations also `admin_audit_log` (`logAdminAction`). Never a message body, phone, CNIC or email in a log or audit row.
- **No free-text subjects.** Subjects/levels are `taxonomy_master` ids (`tutor_subjects`, `job_subjects`), read via `lib/taxonomy.ts` (non-legacy rows only in pickers; `labelsForMasterIds` renders legacy ids). Max **15 distinct subjects** per tutor (`lib/subjectLimitCore.ts`).
- **No search buttons** — every search input is a typeahead (`components/search/Typeahead.tsx`, debounce, `suggest={false}` on admin lists). Applications and admin Tuitions searches also find a tuition by `JOB-TX-…` or `TM-…`, any case, with or without the prefix (`lib/jobCodeSearchCore.ts`).
- No hardcoded secrets, emails, phone numbers or mock data in shipped pages; contact and pay details come from `app_settings` with env fallbacks. No sample data as a form default. No fabricated ratings, counts or reviews.
- Validation: `lib/validate.ts` `parseBody` (Zod; use `z.guid()` not `z.uuid()`); plain human errors, never Zod text. Rate limits live in the DB (`consume_rate_limit`, fails open).
- PostgREST max rows is 1,000 — whole-list reads go through `lib/pageAll.ts`; never `.limit(>1000)` (`test:pagecap`). When asking whether RLS allows something, probe in SQL, not over REST.
- Server code may not import a non-component value from a `'use client'` module (`check:server-imports` runs as prebuild). A client component must never import a file that imports `node:crypto`.
- In-memory caching only: `lib/memoCache.ts` `memoize()` / `invalidateMemoTag()` — no `unstable_cache`, no Data Cache.
- Times: Pakistan time (`Asia/Karachi`) for every day/week/month count; client relative times through `<TimeAgo>`; formatters always pass a `timeZone`.
- `rank_tutors()` must stay `plpgsql` with `SET plan_cache_mode = force_custom_plan` (else signed-in Browse times out).
- After adding a constraint, check the column DEFAULT and triggers too. A public-only dump does not carry `on_auth_user_created` — re-verify it after any restore. `lib/ensureProfile.ts` is the authoritative profile upsert on every user-creating path.

## Security and privacy

- **PERMANENT — TutorMint has exactly one Owner (Alee Sabeer), forever.** Ownership can never be transferred. No role, screen, route, script or migration may create a second Owner, change the Owner's role, or suspend, ban, merge, pause, remove or delete the Owner — nobody can change the Owner's role, access or account. The database enforces it for every caller incl. the service role (migration 215: unique index `profiles_single_owner` + trigger `guard_single_owner`); never write code that disables it.
- **Owner-only actions** (others get 403 and the Owner gets the blocked-attempt alert — `lib/ownerGuard.ts`): suspend / reinstate / ban / lift a ban; change a member's mobile; edit a CNIC number; clear mobile verification; read the CNIC number from a photo; unlock a document for re-upload; rotate/crop a photo; change an already-approved document; approve a home address; reject any payment receipt; approve a receipt with no matching bank credit; reopen a rejected receipt; plan grants; merge, convert account type, close-and-erase, View as; team, roles, staff pause/remove/restore, targets, city owners; Finance actions (link credits, statement import, personal marks, re-label, fee match range, bank details, gateways, refunds); template wording approval; Withdraw a contact / Do not use list; Notification settings, support number, Privacy; Locations approvals; Undo of staff document decisions; Allow / Keep blocked on Blocked re-sign-ups.
- **Every staff role needs two-factor.** A paused staff member has no admin access; their cities and tuitions go to the Owner.
- Masking: phones in admin lists are masked with a logged **Show** (`member.contact_reveal`); CNIC numbers show `XXXXX-XXXXXXX-4`, full number only to the Owner, Project Manager and Backend Support with a logged Show (`cnic.reveal`, written before the value is returned); home addresses the same way — masked "•••••• (City)" with "Read from CNIC — not confirmed" / "Confirmed by member", full address only through the same reviewers' logged Show (`address.reveal`), never public; bank/account numbers show the last 4. Synthetic `@users.tutormint.org` addresses are never displayed (`shownEmail()`). Parents, the public and other tutors never see any part of a CNIC.
- Message number masking: digits that are a Pakistani mobile or CNIC (shape test, `lib/masking.ts`) render masked when either side of the pair lacks contact rights; stored raw.
- Identity documents live only in the private `identity-docs` bucket, served via `/api/documents/[id]/preview` (private, no-store; never through the image optimiser); receipts in private `payment-proofs`. A new document kind is private by default.
- No chat-browsing screen: message bodies load in admin only for a reported message/thread. Official messages use `admin_messages` (Team channel), not `threads`.
- No test data in production; the seed cast is fixed (`npm run reset:seedcast` restores and asserts it). Test-named (`is_test_name`), seed, team and `hidden_from_public` accounts are out of Browse, search, sitemap and every count.
- Credentials only in env; never printed, logged or committed. Never log a phone, email, CNIC, account number, OTP or key.
- View as (Owner only) never signs in as the member: reads run as that member through `lib/viewAsContext.ts`; every write is refused.

## Business rules in force

- **Feels free.** Browsing is public; sign-in is asked only at a transactional action (apply, post, message, view contact, pay), in a small modal that keeps the draft and returns the visitor afterwards (`lib/returnTo.ts` `safeReturnTo`).
- **Verification Fee** — Rs 199, one-time, never "/month", name always **"Verification Fee"** (Urdu تصدیقی فیس), non-refundable. **Upgrades on sale by bank transfer (PR-13):** tutor Premium and parent Featured — "Upgrade to …" on /membership-plans (signed out → sign-in, back to the card; unpaid tutor → the fee first) → /pay/choose receipt + tick → Owner approval activates 30 days (`lib/payments/activate.ts`); the same plan again extends 30 days from its end date, a higher plan replaces with a fresh 30 days, downgrades are never offered and refused (`lib/planPurchaseCore.ts`, `lib/planPurchase.ts`). Tutor Featured is on sale too (PR-14; `PAUSED_UPGRADE_CODES` is empty): its "Matched tuitions on your WhatsApp" line is delivered through People → WhatsApp updates (see below); promotion (`PROMOTE_UPGRADES`: nudges, upsells, Renew reminders) stays off until the Owner turns it on. No refunds, ever. **Non-refundable notice** (`lib/nonRefundableCore.ts`, exact wording): shown above Submit on /pay/choose (a monthly plan shows `NON_REFUNDABLE_PLAN_NOTICE`) with the required tick "I understand the fee is non-refundable" (refused on `/api/payments/receipt` without it; time stored in `payments.non_refundable_ack_at`), in Terms → Fees and refunds (+ the charged-twice line), in the FAQ, and "This fee is non-refundable." on the fee and plan receipt emails and in-app messages. Never an amount in it.
- Tutor plans: Basic (free after the fee), Premium, Featured — see `plans` rows. Displayed quota "Unlimited" hides a real cap; admin sees real numbers.
- **Verified badge** (tutor) = fee paid + CNIC and profile photo submitted and neither rejected (`lib/badgeRule.ts`). Parent badge = CNIC + address approved. Badges never shown that entitlements did not grant.
- **Listing** (`tutor_directory`, mirrored by `lib/tutorListingStatus.ts` `directoryBlockers`; `npm run test:directory:live`): role tutor, not suspended/banned/self-paused/under review/hidden/test/seed/team, verification not suspended/rejected, claimed if imported, no rejected CNIC or photo. The fee is not a listing condition. Profile completion only affects ranking and gaps (`profileGaps`).
- **Selfie is optional everywhere.** Badge, indexing, People stages, status image, social posts rest on CNIC + profile photo. An uploaded selfie still goes to review ("Selfie checked ✓" on member page and own dashboard only).
- **Profile completion** is one rule, `lib/profileRequired.ts` (17 onboarding items for tutors; name, city, verified mobile for parents). Email, intro video and selfie never count.
- **Locked fields** (member side): mobile once verified, CNIC number + pictures once approved, email once a real address is the sign-in address. Everything else is editable any time; a replaced approved photo/selfie waits for review while the approved one stays public (`hold_member_photo` trigger). Locked boxes say "To change your … please contact our support." + WhatsApp. Staff/Owner change them from admin.
- **CNIC address suggestion** (`lib/cnicAddressCore.ts`): a CNIC back upload (and a one-time backfill in the 5-minute cron) reads the address into `address_suggestions` (unconfirmed; service role only) — never for a member who already has an address, nothing saved when the read fails or looks wrong (no known city, mostly symbols). The member sees it under Home address ("We read this from your CNIC. Is this your current address?") and only Confirm or Edit writes `profiles.address`.
- **Two names:** `cnic_name` (legal, never public, locked once CNIC approved) and optional `display_name` (shown publicly; refused if it names TutorMint/staff or is offensive). `full_name` is derived by trigger — never write it as the legal name.
- **Parents** need only a verified mobile to post, message and request demos; CNIC + address are optional (badge only). Hiring and contact need parent Featured (paused).
- **Nothing is deleted** — except personal data erased at the member's own request (Owner on the member page, or the member via Settings with an SMS code; 7-day grace; `lib/accountErase.ts`). Erased accounts keep payments/applications without personal data; the auth user is scrubbed and banned, never deleted. A member with a scheduled erase is excluded from every work list and count. Wherever an erased member still appears (Payments, Finance, statement matches, Applications, People → Deleted, timelines) the row is grey "Deleted user · erased <date>" with the default avatar, no personal detail and no contact/action button except the Owner's money actions (refund, link) — `lib/deletedUserCore.ts`, `components/admin/DeletedUserName.tsx`, `loadErasedAt()`.

## People pipeline and follow-ups

- People (`/admin/users`) tabs: Tutors · Parents · Parents & email not confirmed · Orphaned · Staff. Exclusions (`lib/peopleDirectoryCore.ts` `excludedReason`): staff, seed, team, test, hidden, staff-linked without activity, deleted (own grey chip), erase requested (own chip). Paused accounts stay listed, always last.
- **Stages** (`lib/tutorPipelineCore.ts`, one per tutor): Paid → Rejected → Waiting for approval → Documents missing → Approved, fee pending. Waiting = CNIC and photo uploaded, at least one pending, none rejected, completion ≥ 80%. A file on record with no review status counts as waiting.
- Follow-up chips inside a followed-up stage: Not followed up (due now) · 1st · 2nd · 3rd+ (they add up to the stage). Follow-ups count only since the tutor entered the stage (10-min grace) and same-PKT-day contacts fold into one. Sequence: WhatsApp → voice note 2 days later → WhatsApp or call every 3 days. Calls ask "Reached them?": Yes = follow-up; No answer / Wrong number = attempt only (No answer retries tomorrow). Contacts from the member page and Team inbox count.
- Approved, fee pending lists newest approval first; "Approved today" (approved on today's PKT date, never contacted in the stage) then "Tried to pay" — both subsets of Not followed up, due now — sort first; no-mobile, paused and contacted-in-3-days at the bottom. The card shows "Approved today" all day; the chip drops at the first follow-up (the move is judged at the server's time — `movedJson` `at` — never the browser clock); Overview "Approved today, not contacted" (hidden at 0) and `check:people` (Approved today ⊆ Not followed up) use the same rule; the summary rebuilds on the first run of each PKT day.
- "Not interested" needs a reason, on every stage but Paid; an upload/payment afterwards returns the member automatically.
- Badges count act-now items only: People = documents waiting + Approved · Not followed up; Applications = new applications (last 7 days) no staff member has opened.
- Instant update: every follow-up/decision rewrites that tutor's stored row (`updatePipelineRow`, `syncPipelineSoon` after `logActivity`/`logAdminAction`) and nudges stored badges/Overview rows; the summary job (`lib/adminSummary.ts` → `admin_summary`, `admin_list_rows`, 1-minute cron, automatic rebuild at most every 3 minutes) is the safety net. `npm run check:people` verifies chip sums against lists (read-only, production). `npm run check:inboxstored` builds the Parent interest inbox for its stored copy's own moment and compares (read-only).
- Parents board: one situation message per parent (`lib/parentWhatsApp.ts`), To do / Followed up (3-day wait, 3 messages max). "Tutors applied" is waiting on us.

## Finance and statement import

- Counted revenue = approved, never-refunded payments, dated by approval day (PKT). Refunded/deleted-account payments listed separately, never in totals.
- Receipt approval runs `lib/payments/activate.ts` (the one activation path). An approved payment closes the member's other open checkouts for the same plan (`paid_another_way`). Every Approve/Reject has a 10-second Undo for the decider; the Owner can Reopen a rejected receipt.
- **Fee match range** (default Rs 199–210, Finance setting): a credit in range counts as a fee payment, the extra is `rounding_pkr`. A same-name credit within 48 h links automatically (`lib/feeMatchCore.ts`); a different name is only a suggestion; a credit below range is "Partial" and never activates anything.
- **Statement import** (Owner, `/admin/finance/statement`, `lib/bankStatementCore.ts`): each row stored once by `tran_seq_no`; classified (debit, PayPro settlement = CONTRA 137801949, fee, other); new credits become `bank_transfers` or link to a recorded one; unclear rows ("possibly already recorded") are left out of matching until the Owner decides. Matching: pending receipt by name/reference/mobile; approved bank payment paired only when unique on both sides within ±2 days (Undo stops it pairing again). One credit ↔ one payment, counted once.
- `lib/ignoredCredits.ts` removes from every money total: "Not business (personal)" marks, "Owner / partner transfer" re-labels, "Ignore (not a sale)", refund-due credits.
- PayPro fees are worked out from its settlements (N × 193 covers N × 199; `lib/payproFees.ts`); the export is only a fallback. The Faysal bank email reader is off by default; it never activates anything.
- The reader, matcher and link actions are Owner-only; the Partner views.

## Messaging: email, SMS, WhatsApp, templates

- Email only via `lib/email/send.ts` (`sendOne` priority, `sendBulk` batches of 100, ≤ 5 req/s, retries with idempotency keys, every outcome in `email_sends`). Saving rules `lib/email/policyCore.ts`: per-type switches (Notification settings), 24 h de-dup, daily summary for low-value types, daily limit `email.daily_limit`, never to synthetic/unconfirmed/Do-not-email addresses (critical types always go). Tuition emails never go to the team/staff/test accounts. Staff alerts ring the bell; only the bank-transfer alert emails the Owner.
- Email change uses our own confirmation (`lib/emailConfirm.ts` `requestEmailChange`; one email to the new address, a notice to the old real address) — never `auth.updateUser({ email })`.
- SMS via `sendSms()` (`lib/smsLog.ts`, logged masked in `sms_sends`); one OTP per number at a time, 10-minute life, 5 tries; mobile signup persists nothing until the code verifies (`pending_signups`); hourly SMS health alert.
- **WhatsApp links only through `lib/waLinkCore.ts`** (`waSendHref` → `api.whatsapp.com/send`, never `wa.me` with text — it corrupts emoji; `waChatHref`, `waShareHref`; `finishWaText` puts one full `https://www.tutormint.org` link on its own line; `withStaffRef` adds the sender's `?ref=`). No other file may contain `wa.me/` or `api.whatsapp.com`.
- Templates live in `admin_message_templates` (Team inbox → Templates); live wording changes only on Owner approval (`template_reviews`, `template_history`, `checkWording`: first-name greeting, ≤ 3 lines before one link on its own last-but-one line, then the support line; no emoji, no price except `fu_fee_reply`, no superlative). Retired templates are kept, never sent. Parent WhatsApp is always the situation message.
- **Tutor teasers** (`lib/tutorTeasersCore.ts`, `lib/parentInterestCore.ts`, daily cron): only real counts, nothing when 0, no upsell/price/superlative; paid tutors 2+ days after paying, and unpaid tutors (views, parent interest, new tuitions with "Finish your profile to apply." / "Pay the Verification Fee to apply."; no Monday summary); never erase-requested, Not interested, suspended, banned, paused, unclaimed imports, staff or test; ≤ 3 a Pakistan week (Mon summary, Thu views or the 0-views tip every 14 days, at most one parent-interest alert a day, daily new matching tuitions) plus the uncapped instant "A parent opened your application" (`application_parent_views`, the parent's own tuition page, never under View as) and "Your application for <title, area> was sent to the parent" (first forward only — Forward to parents or the Applied message; `application_forward_alerts`; never under View as or for a test/seed/hidden poster). Parents appear only as `blurName()` ("S**** K****") + city/area — never phone, email or address.
- **Parent interest** (`parent_interest_events`, written by the shortlist, message-start and demo routes through `recordParentInterest`, also for attempts that cannot reach an unpaid tutor): grouped per day into "❤️ N parents from <city> shortlisted your profile / tried to contact you: J**** A****…" (+ "Get verified so parents can contact you." for unpaid). Only real parent accounts count (never staff/test/seed/team/hidden/merged/erased). **Burst check**: > 20 shortlists or > 20 message/demo attempts by one parent in an hour holds that account's events (`interest_holds`, default held); the Owner releases or keeps it on People → WhatsApp updates → Held activity (audit `interest_hold.release`/`.keep`); the account is never changed. The one-time 30-day backfill (5-minute cron, `interest.backfill_done_at`) is sent ≤ 40 tutors a day.
- **People → WhatsApp updates** (`lib/waUpdates.ts`), tab **Today** (Owner, Project Manager, Backend Support — `SCREEN_ACCESS.waUpdates`; every row): paid tutors' application opens and forwards to the parent (an Applied-message Undo removes the forward) and the Monday summary; opted-in tutors only (`tutor_profiles.whatsapp_updates`, default on, Edit Profile). Every send (both tabs) logs `whatsapp_update_sends` (`channel` daily|interest) + audit; one live send a tutor a PKT day (unique index) and ≤ 2 a PKT week across both tabs; Undo (sender or Owner, same day) stamps it; sidebar badge = Today rows to send (Featured items included) + the inbox's ready rows (a city owner: own rows only).

Plain-English message, each title with its own tutormint.org link. ## SEO and public pages

- Public pages are ISR-cached and server-rendered (data in the HTML). **Nothing during a cached page build may read headers/cookies or write to the database** (`renderPhase`, `guardStaticWrites` in `lib/supabase/fetch.ts`); signed-in parts load in the browser via `/api/viewer/*` and `/api/session/header`. Query-string variants rewrite to `/qs/*` twins. Changes revalidate through `lib/publicRevalidate.ts`. Check with `npm run test:staticrender` (+ `:live` after a build).
- Phone budget: ≤ 220 KB gzipped JS per public page (`npm run test:phonebudget`).
- Sitemap = index of `/sitemap-tuitions.xml` (open tuitions only), `/sitemap-tutors.xml` (`tutorProfileIndexable`: fee paid + CNIC and photo approved, not seed/under review; SQL `listed_tutor_slugs()`; lastmod = `tutor_profiles.content_updated_at`, the last change a visitor can see or a subject change), `/sitemap-pages.xml`, `/sitemap-blog.xml`. Every entry passes the same predicate as its page's robots tag (`lib/sitemapCore.ts`). No query strings.
- Landing/hub thresholds: city × subject pages need 3 live items (verified tutors / open tuitions); the main city tuition page is indexable from 1; variants (female/online/area/school) need 3; below it pages render `noindex, follow`. A known city never 404s; the narrower of two ≥ 80%-overlapping landing pages is noindex. Area hubs exist only for curated Locations areas (+ approved aliases).
- **Tutor crawl links** (`lib/tutorCrawlCore.ts`, `lib/tutorCrawl.ts`): `/tutors/<city>` and `/tutors/<city>/female` list the city's tutors with numbered pages (?page= → `/qs/tutors/*` twins), indexable from 3 indexable tutors (3 women for the variant), in `/sitemap-pages.xml`, linked from /browse/tutors and the homepage city area (names only). Each open tuition links ≤ 6 indexable tutors (same city → subject/level → gender preference); each indexable profile links ≤ 6 similar indexable tutors (same city and subject). The Indexing API is never used for profiles.
- **JobPosting** only on open tuitions: description from fields, `employmentType` always, `baseSalary` only with a fee, `validThrough` = base + 20 days, `identifier` = TM number, `hiringOrganization` = TutorMint (or the named school), TELECOMMUTE for online.
- **Indexing API** sends only tuition pages: URL_UPDATED on post/edit/resume/refresh/pause, URL_DELETED only once a page is noindex; ≤ 200 per Pacific day; queued in `indexing_queue`, never during a cached build.
- Titles ≤ 60 (`seoTitle`), descriptions ≤ 155. Organization + WebSite JSON-LD are emitted site-wide by `SiteChrome`; tutor profiles are ProfilePage + Person (no invented rating/offers). `/llms.txt` exists; robots allows all crawlers.
- Only real searches count as demand (`lib/searchCountCore.ts`: bots, own crawlers, staff, cookieless first hits and 30-min repeats are not counted); search rows are written by the browser beacon, not the page render.
