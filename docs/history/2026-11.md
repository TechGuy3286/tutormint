## Hotfix — no header reads or database writes while a cached page is built (owner, 1 Nov 2026)

No migration. Push 3 made public pages cached (ISR); two things then broke first renders with 500 ("Page changed from static to dynamic at runtime", digest DYNAMIC_SERVER_USAGE): the in-memory cache saved its counters to `admin_summary` from inside page renders, and that write made the server Supabase fetch read `headers()` for its "View as" check; and a missing tutor address looked up its old slug with the cookie-scoped client. Rule from now on: **nothing during a cached page build may read request headers or cookies, or write to the database.** `npm run test:staticrender`, `npm run test:staticrender:live` (needs `npm run build`; serves the build locally, loads every kind of cached page fresh and again from the cache, fails on a 500, a page not served from the cache, or "static to dynamic" / DYNAMIC_SERVER_USAGE / `[static-write]` in the log).

- `lib/memoCache.ts` keeps its counters in memory only; the `admin_summary 'cachestats'` save is gone (the row stays, no longer updated).
- `lib/supabase/fetch.ts`: `renderPhase()` reads Next's work unit ('request' = a live request; anything else = building a cached page; none = scripts/proxy). The View-as check reads `headers()` only in a live request. `guardStaticWrites` refuses every write (the same test as the View-as guard — reads and the read-only RPC list pass) while a cached page is built: answered 403 without reaching Supabase and logged `[static-write] refused <method> <path>`.
- `lib/tutorSlug.ts` `currentSlugForRetired` uses the public client (anon may run `tutor_slug_redirect`).
- `check:links` sets `process.exitCode` instead of calling `process.exit()` and catches a crash in its main loop.
